# MCP now: understand the request before choosing an SDK

**Checked:** 2026-10-18. **Read first:** this update, then the numbered lectures for concepts and explicitly dated compatibility examples. **Time:** 30–45 minutes. **Artifact:** a version-labelled request/result transcript and a failure analysis. No paid API or robot hardware is needed for the paper exercise.

The official [versioning page](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) identifies **2026-07-28 as current**. The older `2025-11-25` initialization examples remain useful for existing clients, but changing a date string does not migrate their wire contract. An SDK package version and a protocol revision are different identifiers; verify both endpoints' supported revisions.

## 1. The two contracts

| Question | 2025-11-25 compatibility examples | Current 2026-07-28 contract |
|---|---|---|
| How is the version established? | `initialize`, then `notifications/initialized` | Version and client capabilities accompany every request |
| Must the client discover first? | Initialization begins the session | Server implements `server/discover`; client may use it before another operation |
| Does a connection identify a conversation? | Some examples rely on protocol sessions | No; cross-call application state uses explicit handles |
| What marks a completed result? | `result` without a discriminator | `resultType: "complete"` |
| How does additional input flow? | Server-initiated reverse requests | An `input_required` result followed by a retry carrying input responses |

The first two rows follow [versioning and compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning); the message/state distinctions follow the [base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index) and [multi round-trip pattern](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr). A dual-era endpoint may serve both contracts. A current-only client does not automatically interoperate with an old-only server.

The current [change log](https://modelcontextprotocol.io/specification/2026-07-28/changelog) also removes protocol session headers and SSE replay, replaces old resource subscriptions with `subscriptions/listen`, adds cache metadata to cacheable results, and moves long-running Tasks into an extension. These are behavior changes that deserve tests, not a configuration-only upgrade.

## 2. Work one robot-status request by hand

Assume the server has already advertised a read-only `robot_status` tool accepting `robot_id`. This is a **constructed transcript**, not a claim of an executed SDK integration. The request body is:

```json
{
  "jsonrpc": "2.0",
  "id": "status-17",
  "method": "tools/call",
  "params": {
    "name": "robot_status",
    "arguments": {"robot_id": "sim-01"},
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": {
        "name": "course-transcript-reader",
        "version": "1.0"
      }
    }
  }
}
```

A successful teaching response is:

```json
{
  "jsonrpc": "2.0",
  "id": "status-17",
  "result": {
    "resultType": "complete",
    "content": [{"type": "text", "text": "sim-01 is idle"}],
    "isError": false,
    "_meta": {
      "io.modelcontextprotocol/serverInfo": {
        "name": "course-status-server",
        "version": "1.0"
      }
    }
  }
}
```

Compare the ID, method, argument schema, metadata, and result type with the [tool specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). This body alone is not a complete HTTP exchange: the transport has its own required headers and authorization contract. A tool description or self-reported client name does not authenticate a caller.

**Guided variation A:** remove `io.modelcontextprotocol/clientCapabilities`. **Answer:** the current base protocol requires that field even when its value is `{}`; the request is malformed (`-32602`, and HTTP 400 on that transport).

**Guided variation B:** use an unsupported protocol version. **Answer:** distinguish `UnsupportedProtocolVersion` (`-32022`) from malformed parameters. Select a mutually supported revision or report incompatibility; do not silently interpret the same body using an unrelated older contract.

**Guided variation C:** the client loses the reply and sends a new request ID. Did the operation happen once? **Answer:** the transport cannot establish that. Reading status again is different from repeating a state-changing operation. A mutating service needs application-level deduplication or an explicit outcome query; a new JSON-RPC ID is not an idempotency key.

## 3. Learn the current feature boundaries

Tools, resources, prompts, and elicitation remain the useful starting concepts. **Roots, Sampling, and Logging are deprecated**, not yet removed; the [deprecated-feature registry](https://modelcontextprotocol.io/specification/2026-07-28/deprecated) defines their status. Treat Lecture 04's reverse-primitives examples and Lecture 05's related `Context` methods as compatibility study. Do not add new dependencies on those features merely because an old SDK exposes them.

MCP Apps, Tasks, and other extensions need explicit support from both sides. The base protocol being stateless does not erase application state, authorization, or long-running work. For robotics, a supervisory status/task interface is separate from a real-time control loop and must keep its existing action bounds and watchdog behavior.
